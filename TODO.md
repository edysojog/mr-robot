## Strix-inspired ideas
Positioning was "detection → understanding → fix" with no dynamic execution -- deliberately revisited: the chat CLI now has an opt-in `--enable-validation` mode.
- [x] **Live finding validation** (`src/cli/chat.js`) — two more agent tools, `http_request` (sends one real HTTP request against a target you're running) and `run_command` (runs one real shell command on your machine), gated behind `--enable-validation` (off by default -- the tool list itself excludes them unless passed) plus a per-call `confirmFn` prompt that shows the exact request/command and requires an explicit `y` before anything executes; a decline returns `{declined: true, ...}` and the system prompt tells the model not to fabricate a result when declined. This is the actual Strix-shaped capability (prove a finding instead of just discussing it) rather than a scaled-down imitation -- unlike Strix there's no sandbox, so `run_command` executes directly on the user's machine, which is why the default is off and every call is gated. Verified directly: tool-list length with/without the flag, decline path on both tools, approved `run_command` actually executing (`echo` output captured), and `http_request` hitting a real local HTTP server and returning its actual response.
- [ ] **AI-suggested fix diffs** — per confirmed finding, generate a reviewable unified diff instead of just a text description. Highest dev-value item on this list; fits the existing human-review model (report, never auto-apply).
- [ ] **PoC narrative per finding** — LLM writes out the concrete exploitation path (example payload/request) grounded in the actual code, without executing anything.
- [x] **Chat-style Q&A on findings** — done two ways. (1) "ask about this" button per finding in the GUI results screen (see below). (2) **Interactive chat CLI** (`src/cli/chat.js`, `npm run chat` / `mrrobotbot-chat`) — a Claude-Code-style REPL, not a one-shot flag command: you talk to it in plain English ("scan this project", "what's finding 3 about", "is finding 1 a false positive") and an agentic loop (Claude tool_use or Groq OpenAI-style function calling, provider picked via `--provider`) decides when to call `scan_project` / `list_findings` / `explain_finding` tools, which wrap the exact same scan services `src/cli/index.js` already uses (fileWalker/semgrepRunner/gitleaksRunner/npmAuditRunner/findingsMerger/claudeAuditor/groqAuditor) plus `chatService.chat()` for the explain step. Session-scoped state only (last scan + per-finding chat history), no persistence. Same "explain only, never propose a fix" system-prompt rule as the GUI chat. Claude/Groq only, matching every other "confirmed provider" feature in this file. Verified: tool logic (list/filter/error-paths) exercised directly with no network calls; the agent loop itself needs a live API key to test end-to-end, which isn't available in this environment (same untested-live-key caveat as the rest of the AI-pass features here).
